:::user
파이썬을 알기 위해선 어떤걸 알아야 하나요?
:::

:::assistant
크게 네 가지를 알아야 합니다.

| 갈래 | 질문 |
|---|---|
| **언어 특성** | 입문자에게 좋은 이유와 대규모 개발의 한계, 소스 코드가 실행되기까지의 과정 |
| **이터레이션** | Iterable과 Iterator의 차이, Generator가 일반 함수와 다른 점 |
| **예외** | 예외가 조건문보다 비싼 이유, 모든 코드를 try로 감싸도 되는지 |
| **실전** | 디버깅 순서, 메모리 부족 대응, 복잡도 관리, 그리고 이걸 전부 묶어서 대규모 프로젝트에 적용하는 원칙 |

개념 정의만 묻지 않고 **"그래서 실제로는 어떻게 할 건데?"로 이어지는 질문**이 많았습니다. 아래에 질문마다 정리한 답을 남깁니다.
:::

:::user
왜 다들 파이썬으로 입문하라고 해?
:::

:::assistant
세 가지 이유가 있습니다.

1. **문법이 읽히는 대로 동작합니다.** 중괄호와 세미콜론 대신 들여쓰기로 블록을 나눠서, 코드 모양이 곧 구조입니다. `for item in items:`처럼 영어 문장에 가깝게 읽힙니다.
2. **피드백이 빠릅니다.** 타입 선언과 컴파일 단계 없이 바로 실행되고, REPL이나 Jupyter에서 한 줄씩 결과를 확인할 수 있습니다. 입문 단계에서는 "써 보고 바로 확인"하는 반복 횟수가 곧 학습 속도입니다.
3. **표준 라이브러리와 생태계가 넓습니다.** 파일, JSON, HTTP, 날짜 처리가 기본으로 들어 있고(batteries included), `pip install` 한 줄로 데이터 분석·웹·AI 라이브러리까지 붙일 수 있어서 배운 걸 바로 결과물로 만들기 좋습니다.
:::

:::user
그럼 대규모 서비스를 만들 때 생기는 문제는 뭐야?
:::

:::assistant
입문자에게 장점이었던 특성이 규모가 커지면 그대로 비용이 됩니다.

| 한계 | 원인 | 보완 방법 |
|---|---|---|
| **타입 오류가 실행 시점에 드러남** | 동적 타이핑이라 잘못된 타입이 들어가도 그 줄이 실행되기 전까지 모름. 리팩터링할 때 영향 범위를 파악하기 어려움 | 타입 힌트 + mypy/pyright를 CI에 걸기 |
| **CPU 연산이 느림** | 바이트코드를 인터프리터가 한 줄씩 실행 | NumPy 같은 C 확장, 병목 구간만 다른 언어로 분리 |
| **멀티스레드로 CPU 병렬화가 어려움** | CPython의 GIL 때문에 한 번에 한 스레드만 바이트코드를 실행 | I/O는 asyncio·스레드, CPU 작업은 multiprocessing. 3.13부터 GIL 없는 빌드가 실험적으로 들어옴 |
| **의존성·배포 관리** | 패키지 버전 충돌, 환경마다 다른 인터프리터 | `uv`/`poetry`로 lock 파일 고정, 컨테이너로 실행 환경 통일 |

결국 "파이썬은 대규모 개발에 안 맞는다"가 아니라, **언어가 기본으로 보장해 주지 않는 것을 도구와 규칙으로 채워야 한다**는 쪽으로 답했습니다.
:::

:::user
파이썬은 인터프리터 언어라는데, 컴파일은 아예 안 해?
:::

:::assistant
합니다. 다만 **기계어가 아니라 바이트코드로** 컴파일합니다. CPython 기준으로 이렇게 흘러갑니다.

1. **토큰화 · 파싱**: 소스 코드를 토큰으로 쪼개고 AST(추상 구문 트리)를 만듭니다. 문법 오류(`SyntaxError`)는 여기서 걸립니다.
2. **바이트코드 컴파일**: AST를 파이썬 가상 머신이 이해하는 바이트코드로 바꿉니다. import된 모듈은 `__pycache__/*.pyc`로 캐시해서 다음 실행 때 이 단계를 건너뜁니다.
3. **PVM 실행**: 인터프리터 루프가 바이트코드 명령을 하나씩 꺼내 실행합니다. 타입 확인도 이 시점에 합니다.

```python
import dis

def add(a, b):
    return a + b

dis.dis(add)
# LOAD_FAST a / LOAD_FAST b / BINARY_OP (+) / RETURN_VALUE
```

C 같은 컴파일 언어와 비교하면 이렇습니다.

| | C (컴파일 언어) | 파이썬 (CPython) |
|---|---|---|
| 번역 결과 | CPU가 바로 실행하는 기계어 | 가상 머신용 바이트코드 |
| 번역 시점 | 실행 전에 한 번 (빌드) | 실행할 때마다 (캐시 있으면 생략) |
| 타입 검사 | 컴파일 시점 | 실행 시점 |
| 실행 속도 | 빠름 | 명령마다 해석 비용이 있어 느림 |
| 이식성 | 플랫폼별로 다시 빌드 | 인터프리터만 있으면 같은 코드 실행 |

그래서 "인터프리터 언어"보다는 **"바이트코드로 컴파일한 뒤 인터프리터가 실행하는 언어"** 가 정확한 표현입니다. 3.11부터는 자주 실행되는 명령을 타입에 맞게 특수화하는 최적화가 들어갔고, 3.13에는 실험적인 JIT도 추가됐습니다.
:::

:::user
for문은 내부적으로 어떻게 돌아가?
:::

:::assistant
**Iterable에서 Iterator를 꺼내고, `StopIteration`이 날 때까지 `next()`를 부르는 구조**입니다.

| | Iterable | Iterator |
|---|---|---|
| 의미 | 순회할 수 있는 대상 | 순회 중인 상태(현재 위치)를 가진 객체 |
| 필요한 메서드 | `__iter__()` | `__iter__()`(자기 자신 반환) + `__next__()` |
| 예 | `list`, `str`, `dict`, `range` | `iter([1, 2])`, 파일 객체, 제너레이터 |
| 재사용 | 몇 번이든 새로 순회 가능 | 한 번 소진되면 끝 |

`iter()`는 Iterable의 `__iter__()`를 불러 Iterator를 만들고, `next()`는 Iterator의 `__next__()`를 불러 값을 하나 꺼냅니다. for문은 이 둘을 대신 불러 주는 문법입니다.

```python
nums = [1, 2, 3]          # Iterable
it = iter(nums)           # Iterator
next(it)  # 1
next(it)  # 2
next(it)  # 3
next(it)  # StopIteration

# for n in nums: 는 실제로 이렇게 동작합니다
it = iter(nums)
while True:
    try:
        n = next(it)
    except StopIteration:
        break
    ...
```

역할을 나눈 이유는 **하나의 데이터를 여러 곳에서 동시에 독립적으로 순회**하기 위해서입니다. 리스트는 위치를 모르고, 위치는 매번 새로 만든 Iterator가 따로 들고 있습니다.
:::

:::user
yield를 쓰면 함수가 뭐가 달라져?
:::

:::assistant
함수가 **한 번 실행되고 끝나는 것이 아니라, 멈췄다가 이어서 실행되는 객체**가 됩니다.

| | 일반 함수 | 제너레이터 함수 |
|---|---|---|
| 호출하면 | 본문을 끝까지 실행하고 값을 반환 | 본문을 실행하지 않고 제너레이터 객체만 반환 |
| 값 전달 | `return`으로 한 번 | `yield`로 여러 번 |
| 지역 변수 | 반환하면 사라짐 | `yield`에서 멈춘 상태로 보존 |
| 끝나면 | 호출자에게 값 반환 | `StopIteration` 발생 |

```python
def countdown(n):
    print("시작")
    while n > 0:
        yield n
        n -= 1

gen = countdown(3)   # 아직 "시작"도 출력되지 않음
next(gen)            # "시작" 출력 후 3에서 멈춤
next(gen)            # n -= 1부터 이어서 실행 → 2
```

`next()`가 불릴 때마다 직전 `yield` 다음 줄부터 이어서 실행하고, 다음 `yield`에서 다시 멈춥니다. 실행 위치와 지역 변수를 담은 프레임이 살아 있기 때문에 가능한 동작입니다.

제너레이터는 Iterator이기도 해서 앞에서 말한 for문에 그대로 쓸 수 있고, **값이 필요할 때만 하나씩 만들기 때문에(lazy evaluation) 전체 결과를 메모리에 올리지 않습니다.** 대신 한 번 소진되면 다시 순회할 수 없습니다.
:::

:::user
try-except를 쓰면 느려진다는 말이 맞아?
:::

:::assistant
반은 맞습니다. **예외가 실제로 발생했을 때** 비용이 큽니다.

예외가 발생하면 파이썬은 이런 일을 합니다.

- 예외 객체를 생성합니다.
- 발생 위치부터 호출 스택을 거슬러 올라가며 트레이스백을 만듭니다.
- 맞는 `except`를 찾을 때까지 프레임을 하나씩 정리(스택 되감기)합니다.

조건문은 값 하나를 비교하고 분기하면 끝이라 이 과정이 없습니다. 반면 `try`에 들어가는 것 자체는 거의 공짜입니다. 3.11부터는 예외가 없으면 비용이 0에 가까운 zero-cost 방식으로 바뀌었습니다.

그래서 기준은 **실패가 얼마나 자주 일어나느냐**입니다.

```python
# 키가 거의 항상 있다 → EAFP(일단 시도)가 자연스럽고 빠름
try:
    value = cache[key]
except KeyError:
    value = load(key)

# 키가 없는 경우가 흔하다 → 예외를 매번 만들지 말고 조건으로 처리
value = cache.get(key)
if value is None:
    value = load(key)
```

- 실패가 드문 경우: `try`로 감싸는 EAFP 스타일이 읽기 좋고 성능도 손해가 없습니다.
- 실패가 흔한 경우, 특히 반복문 안이라면: 조건문(LBYL)이나 `dict.get()`, `getattr(obj, name, default)`처럼 예외를 만들지 않는 API를 씁니다.
- 예외를 반복문 탈출 같은 **일반적인 흐름 제어용으로 쓰지 않습니다.**
:::

:::user
그럼 에러 날 것 같은 코드는 전부 try로 감싸면 돼?
:::

:::assistant
아닙니다. 무조건 감싸면 **버그가 조용히 묻혀서** 오히려 원인을 찾기 어려워집니다.

```python
# 나쁜 예: 무슨 일이 있어도 넘어감
try:
    user = get_user(user_id)
    send_email(user.email)
except Exception:
    pass
```

여기서 `get_user`의 오타, `None` 접근, 네트워크 장애가 전부 같은 방식으로 사라집니다. 저는 이런 기준으로 판단합니다.

1. **여기서 처리할 수 있는가?** 재시도, 기본값, 사용자에게 안내 같은 대응이 가능할 때만 잡습니다. 할 수 있는 게 없으면 위로 올려 보냅니다.
2. **예상 가능한 실패인가, 버그인가?** 파일 없음, 네트워크 타임아웃, 잘못된 사용자 입력처럼 외부 요인은 잡습니다. `TypeError`, `AttributeError`처럼 코드 실수는 잡지 말고 빨리 터지게 둡니다.
3. **구체적인 예외만** 잡습니다. `except Exception`이나 맨 `except:`는 프로그램 최상단의 로깅 지점 정도에서만 씁니다.
4. **try 범위는 좁게** 둡니다. 실패할 수 있는 한 줄만 감싸야 다른 줄의 버그까지 삼키지 않습니다.
5. 잡았다면 **흔적을 남깁니다.** 로그를 찍거나, 도메인 예외로 바꿀 때 `raise ... from e`로 원래 원인을 이어 붙입니다.

```python
try:
    resp = client.get(url, timeout=5)
except httpx.TimeoutException as e:
    raise ExternalServiceError("결제 서버 응답 없음") from e
```

리소스 정리가 목적이라면 `try-except`보다 `with`(컨텍스트 매니저)나 `finally`가 맞습니다.
:::

:::user
예상 못한 에러가 나면 어디부터 봐?
:::

:::assistant
감으로 코드를 고치기 전에 **범위를 좁히는 순서**로 봅니다.

1. **트레이스백을 아래에서부터 읽습니다.** 마지막 줄의 예외 종류와 메시지, 그리고 스택 중 *내 코드*의 마지막 프레임이 출발점입니다. 라이브러리 내부 프레임보다 내가 넘긴 값이 원인인 경우가 대부분입니다.
2. **재현합니다.** 같은 입력으로 다시 일으킬 수 있는지 확인하고, 가능하면 입력을 최소한으로 줄입니다. 재현이 안 되면 타이밍, 환경, 외부 데이터 문제를 의심합니다.
3. **가정을 확인합니다.** "여기는 항상 리스트가 들어온다", "이 값은 None이 아니다" 같은 가정을 `breakpoint()`(pdb)나 로그로 실제 값과 비교합니다.
4. **최근 변경을 봅니다.** 어제는 됐다면 `git diff`, 범위가 넓으면 `git bisect`로 원인 커밋을 찾습니다.
5. **환경을 확인합니다.** 파이썬·패키지 버전, 가상환경, 환경 변수, 입력 파일 인코딩처럼 코드 밖의 차이입니다.
6. **고치기 전에 재현 테스트를 먼저 씁니다.** 테스트가 실패하는 걸 확인하고 고치면, 같은 버그가 다시 들어오는 걸 막을 수 있습니다.
:::

:::user
데이터가 너무 커서 메모리가 터지면 어떻게 해?
:::

:::assistant
먼저 **어디서 메모리를 쓰는지 측정**하고(`tracemalloc`, `memory_profiler`), 그다음 아래 방법을 순서대로 검토합니다.

**1. 한 번에 다 올리지 않기**

가장 효과가 큰 방법입니다. 리스트로 모으지 말고 제너레이터로 흘려보내면 메모리 사용량이 데이터 크기와 무관해집니다.

```python
# 전체를 메모리에 올림
rows = [parse(line) for line in open("big.log")]

# 한 줄씩 처리
def read_rows(path):
    with open(path) as f:
        for line in f:
            yield parse(line)

total = sum(row.size for row in read_rows("big.log"))
```

pandas도 `read_csv(..., chunksize=100_000)`로 나눠 읽을 수 있습니다.

**2. 더 가벼운 표현 쓰기**

| 상황 | 방법 |
|---|---|
| 숫자가 많은 리스트 | `array` 모듈이나 NumPy 배열 (원소마다 파이썬 객체를 만들지 않음) |
| 같은 구조의 객체가 수백만 개 | 클래스에 `__slots__` 지정 |
| pandas 컬럼 | `int64` → `int32`, 반복되는 문자열은 `category` |

**3. 필요 없는 참조 끊기**

큰 중간 결과를 다 쓴 뒤에도 변수가 잡고 있으면 해제되지 않습니다. 함수로 범위를 나누거나 `del`로 참조를 끊습니다.

**4. 메모리 밖에서 처리하기**

그래도 부족하면 데이터를 메모리에 두지 않습니다. SQLite나 DuckDB에 넣고 쿼리하거나, Parquet처럼 필요한 컬럼만 읽을 수 있는 포맷을 쓰거나, 데이터를 나눠 여러 프로세스·머신에서 처리합니다.
:::

:::user
코드가 점점 복잡해지는 건 어떻게 막아?
:::

:::assistant
복잡도는 한 번에 생기지 않고 조금씩 쌓이기 때문에, **쌓이는 속도를 늦추는 습관**과 **자동으로 막아 주는 장치**를 같이 둡니다.

**작성할 때**
- 함수 하나는 한 가지 일만 합니다. 이름을 짓기 어렵거나 "그리고"가 들어가면 쪼갤 신호입니다.
- 이름으로 의도를 드러냅니다. 주석은 *무엇*이 아니라 *왜*를 적습니다.
- 입력 검증, 비즈니스 로직, 외부 I/O를 섞지 않고 분리합니다. 로직이 순수 함수에 가까울수록 테스트하기 쉽습니다.
- 당장 필요 없는 추상화는 만들지 않습니다. 같은 패턴이 세 번쯤 반복되면 그때 묶습니다.

**관리할 때**
- 테스트가 있어야 리팩터링을 할 수 있습니다. 테스트 없는 코드는 고치기 무서워서 복잡한 채로 남습니다.
- `ruff`(린트·포맷), `mypy`(타입)를 CI에 걸어서 스타일과 타입 문제는 사람이 리뷰하지 않게 합니다.
- 기능을 추가하기 전에 그 기능이 들어가기 쉽게 구조부터 정리합니다.
- 코드 리뷰에서 "이해가 안 된다"는 피드백을 버그와 같은 무게로 봅니다.
:::

:::user
큰 프로젝트에서는 타입 힌트, 예외, 제너레이터를 어떻게 같이 써?
:::

:::assistant
세 가지를 **"경계에서 검증하고, 안쪽은 믿고, 흐름은 스트리밍한다"** 는 원칙으로 묶습니다.

| | 원칙 | 장점 | 한계 |
|---|---|---|---|
| **타입 힌트** | 모듈 간 공개 함수와 데이터 구조는 반드시 타입을 명시하고 CI에서 정적 검사. 외부 입력은 Pydantic으로 런타임 검증 | 실행 전에 오류 발견, IDE 자동완성, 문서 역할 | 런타임에 강제되지 않음. `Any`가 섞이면 검사가 무력화됨 |
| **예외** | 도메인별 예외 계층(`AppError` → `NotFoundError` 등)을 만들고, 외부 라이브러리 예외는 경계에서 도메인 예외로 변환. 처리는 최상단(API 핸들러 등) 한 곳에서 | 정상 흐름과 오류 흐름이 분리되어 코드가 읽기 쉬움 | 함수 시그니처에 드러나지 않아 어떤 예외가 나올지 문서와 테스트로 보완해야 함 |
| **Iterator / Generator** | 대량 데이터는 "읽기 → 검증 → 변환 → 저장"을 제너레이터 단계로 이어 붙임. 반환 타입은 `Iterator[T]`로 명시 | 메모리 사용량 일정, 단계별로 테스트 가능 | 한 번만 순회 가능, 오류가 생성 시점이 아니라 **소비 시점**에 터져서 디버깅이 어려움 |

세 가지를 함께 쓰면 이런 모양이 됩니다.

```python
from collections.abc import Iterator
from pydantic import BaseModel, ValidationError

class Order(BaseModel):
    id: int
    amount: int

class AppError(Exception): ...
class InvalidRecordError(AppError): ...

def parse_orders(lines: Iterator[str]) -> Iterator[Order]:
    for lineno, line in enumerate(lines, 1):
        try:
            yield Order.model_validate_json(line)
        except ValidationError as e:
            raise InvalidRecordError(f"{lineno}번째 줄") from e
```

- 타입이 각 단계의 입출력을 약속하고,
- 잘못된 레코드는 위치가 담긴 도메인 예외로 바뀌어 올라가고,
- 파일이 아무리 커도 한 줄씩만 메모리에 있습니다.

제너레이터의 한계를 보완하려고 두 가지를 더 지킵니다. **제너레이터 안에서 파일·커넥션을 열 때는 `with`로 감싸서** 중간에 소비를 멈춰도 정리되게 하고, **여러 번 순회해야 하는 데이터는 제너레이터로 넘기지 않습니다.**
:::
