가장 고민이 많았던 의사결정은 뭐야?

:::assistant
**임베딩을 로컬 GPU에서 API로 바꾼 일**입니다.

개발 단계에서는 로컬 Ollama의 `qwen3-embedding:8b`(4096차원)로 인덱스를 구축했습니다. 로컬이라 쿼터 제한 없이 데이터 테스트를 빠르게 반복할 수 있었습니다.

그런데 이 모델을 그대로 배포에 쓰기엔 비용 부담이 컸습니다. AI 서버가 처리해야 하는 건 벡터 임베딩 자체가 아니라 **검색어가 들어올 때마다 이를 벡터로 변환하는 임베딩 추론 요청**입니다. 즉 `qwen3-embedding:8b`를 서빙하려면 GPU 인스턴스를 상시 띄워둬야 하고, 트래픽이 없는 시간에도 비용이 그대로 발생하는 구조였습니다.

그래서 모델을 직접 서빙하는 대신 API 임베딩으로 전환했습니다. 서버는 트래픽이 없으면 0으로 스케일 다운되는 **Cloud Run CPU 컨테이너**를 쓰고, 임베딩 비용은 실제 호출량만큼만 지불하도록 구조를 바꿨습니다.
:::

:::user
어떤 모델로 바꿨고, 왜 그걸 골랐어?
:::

:::assistant
여러 임베딩 모델을 테스트한 결과 **Upstage `embedding-2`** 가 한국어 검색 품질이 가장 좋았고 코스 생성 품질도 뛰어났습니다.

| 항목 | 판단 |
|---|---|
| **한국어 검색 품질** | 검색어와 문서를 서로 다른 모델로 임베딩하는 비대칭 구조(`embedding-2-query` / `-passage`)입니다. `"비 오는 날 실내에서 조용히 볼 만한 전시"` 같은 문장이 실제 전시·실내 장소로 잘 걸리는 걸 확인했고, 코스 품질도 qwen3 때와 차이가 없었습니다 |
| **쿼터** | 2,000 RPM · 700,000 TPM에 하루 한도가 없습니다. 1,648청크를 통째로 다시 넣어도 기다림 없이 한 번에 끝납니다 |
| **인덱스 크기** | 1024차원이라 4096차원 대비 인덱스가 1/4로 줄었습니다 (`data/chroma` 62M → 20M). 배포 이미지도 그만큼 가벼워집니다 |

덤으로 얻은 것도 있습니다. 임베딩이 챗 LLM과 완전히 따로 놀기 때문에, **챗 모델을 바꿔도 인덱스를 다시 구울 필요가 없습니다.** 프로바이더 스위치로 챗 LLM을 갈아끼워도 검색 계층은 그대로입니다.
:::
