:::user
관광객이랑 현지인은 어떻게 다르게 처리해?
:::

:::assistant
사람 구분은 `audience`(`local` | `tourist`) 하나뿐이고, **코드에서 실제로 갈라지는 곳은 딱 세 군데**입니다. 나머지는 전부 같은 함수를 씁니다.

| 갈라지는 곳 | `tourist` | `local` |
|---|---|---|
| `_base_window()` — 시간 칩이 없을 때 | 기본 여행 시간을 09~21시로 설정 (여행자는 하루 단위 코스라서) | 시간창을 만들지 않음 → 시각 없는 자유 방문 코스 |
| `_day_areas()` — 여러 날 요청일 때 | 일차별로 권역을 나눠 배정 | 항상 한 권역만 선택 |
| `summary()` 프롬프트 라벨 | `"서울 여행자"` | `"시민"` |

이 중 `_day_areas()` 결과가 있느냐 없느냐가 뒤따르는 `retrieve` · `select_places` · `fit_schedule` 세 노드의 동작까지 바꿉니다.
:::

:::user
일부러 합쳐 둔 부분도 있어?
:::

:::assistant
네. 갈래를 늘리지 않으려고 의도적으로 공유한 지점들입니다.

- `locations`를 하나만 고른 여행자는 현지인과 똑같이 단일 권역으로 갑니다. "그 동네에서만 놀고 싶다"는 뜻이라 나눌 이유가 없습니다.
- `retrieve`의 차이는 **루프를 도느냐 마느냐뿐**입니다. 안에서 쓰는 `_search_pool` → `_geo_rerank` → `_dedupe_same_place` → `_quota_pick`은 완전히 같은 함수입니다. 일차별 호출은 시드에 일차 번호만 더합니다(`seed + d`).
- `select_places`의 병렬 N콜도 프롬프트가 다른 게 아니라 **후보 목록만 일차별로 잘라 넣은 같은 콜**입니다. 후보에 `day_hint`가 박혀 있어서 서로 겹칠 수가 없습니다.
- `fit_schedule`은 앵커 좌표만 다르고 순열 탐색·예산 배분 로직은 하나입니다 (`day_areas`가 없으면 위치 칩으로 폴백).
- `meals`부터 `compose`까지 4개 노드는 **분기가 아예 없습니다.** 여행자든 현지인이든 그 시점엔 "확정된 스톱 목록 + 시간표"라는 같은 모양이 되어 있기 때문입니다.

분기를 세 군데로 묶어 두니 새 조건을 추가할 때 건드릴 곳이 어디인지 바로 보입니다.
:::
